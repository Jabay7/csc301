Prerequisites

The slice of Java this course actually uses

You are not relearning all of Java. Data Structures II uses a narrow subset, over and over: classes, generics, compareTo, and recursion over a node. No streams, no lambdas.

References vs. values

This is the idea the whole course sits on. A variable holding an object holds a reference — an arrow pointing at the object — not the object itself. Two variables can point at the same thing.

// both names point at ONE array
int[] x = {1, 2, 3};
int[] y = x;
y[0] = 99;
x[0]  // 99 — x changed too

Every tree and graph in this course is nodes holding references to other nodes. When your BST misbehaves at 11pm, the fix is almost always to draw it: box for the object, arrow for the reference.

Reassigning a reference does not modify what it pointed at. That is precisely why BST deletion is written as node.left = delete(node.left, key) — you are rebuilding links on the way back up the recursion.

== vs. .equals()

Integer a = 128, b = 128;
a == b        // false — compares references
a.equals(b)   // true  — compares values
Costs people an afternoon

== for primitives, .equals() for objects. Comparing strings with == sometimes works by accident, which is worse than never working.

The node class

Nearly every structure you write this quarter starts here.

public class BST<Key extends Comparable<Key>, Value> {

    private Node root;

    private class Node {          // inner: nobody outside needs it
        Key key;
        Value val;
        Node left, right;
        int size;

        Node(Key key, Value val) {
            this.key = key;
            this.val = val;
            this.size = 1;
        }
    }
}

Read the generics out loud: Key extends Comparable<Key> means “whatever type Key is, it must know how to compare itself to another Key.” That’s what makes key.compareTo(node.key) legal inside. Value has no bound — any type at all.

The search shape

You will type a variant of this perhaps forty times this quarter. Learn it as a story, not as characters.

private Value get(Node x, Key key) {
    if (x == null) return null;              // nothing here
    int cmp = key.compareTo(x.key);
    if      (cmp < 0) return get(x.left,  key);  // smaller — go left
    else if (cmp > 0) return get(x.right, key);  // bigger — go right
    else              return x.val;              // found it
}
The story

Nothing here? Smaller, go left. Bigger, go right. Otherwise this is it. Every BST, 2–3 tree, and red–black tree operation is a variation on those four lines.

Recursion, without holding the stack in your head

Every recursive method has exactly two parts: a base case small enough to answer immediately, and a recursive case that does a little work then calls itself on a strictly smaller input. Miss either and you get StackOverflowError.

The skill that unblocks people is refusing to trace the whole call stack mentally. It doesn’t fit, and trying is why recursion feels impossible. Instead, assume the recursive call already works:

The leap

“size(x.left) correctly returns the number of nodes on the left. size(x.right) correctly returns the right. So I add them and count myself.”

private int size(Node x) {
    if (x == null) return 0;
    return 1 + size(x.left) + size(x.right);
}

private int height(Node x) {
    if (x == null) return -1;
    return 1 + Math.max(height(x.left), height(x.right));
}

Both are the same three lines: check null, combine the subtrees, add yourself. Verify only two things — the base case is right, and the input genuinely got smaller.

The three Java ideas people actually get stuck on

Think of it like — references

A reference is a street address written on a slip of paper, not the house itself.

Copy the slip and you have two slips with the same address — one house. Paint that house and both slips describe a painted house. That's why changing an array through one variable changes it through the other.

Now scribble out one slip and write a different address. The original house isn't touched at all; you just stopped pointing at it. That's reassignment, and it's why node = newNode inside a method doesn't change the caller's tree — you edited your own slip.

This is the single reason x.left = put(x.left, ...) is written that way.

Think of it like — null

null is a slip of paper with nothing written on it. It isn't an empty house — there's no house.

So node.left.key when node.left is null is asking "what's the key of the house at [blank]?" That's the NullPointerException. In tree code, null means "the tree ends here," which is why almost every recursive method opens with if (x == null).

Think of it like — generics

<Key extends Comparable<Key>> is a job posting with a requirement: "any type may apply, but you must know how to compare yourself to others of your kind."

String qualifies — it knows alphabetical order. Integer qualifies. A Student class you wrote qualifies only if you implemented compareTo. Without that requirement in the signature, the compiler wouldn't let you write key.compareTo(x.key) — it'd have no reason to believe the method exists.

The recursion mindset, one more time

Think of it like

Counting how many people are in a long line, without leaving your spot.

You tap the person ahead and ask "how many are in front of you?" — then add one and pass it back. You don't care how they get their number. You trust them.

The person at the front has nobody ahead, says "zero," and the answers cascade back. That's the base case, and it's the only place where an actual answer is produced rather than delegated.

Don't trace the whole chain. Verify two things: the front person answers correctly, and everyone else asks someone strictly closer to the front.

Where people go wrong

Wrong: Trying to hold every recursive call in your head at once.

Right: That doesn't fit in anyone's head past about three levels, and trying is why recursion feels impossible. Assume the recursive call already works. Check the base case, check the input shrinks, move on. StackOverflowError means exactly one of those two checks failed.

Say it out loud

Until this is natural

“Binary search is O(log n) because each comparison throws away half of what’s left. Starting from n items, I can only halve n about log₂n times before there’s one left.”

If you can produce that unprompted, you understand Big-O well enough for this course. The whole thing rests on one observation: halving and doubling are the same question. “How many times do I double 1 before I reach n?” is the definition of log₂n. Binary search halves the range each step, so it asks the identical question and gets the identical answer.

That’s also why half this course is about keeping trees balanced. A balanced tree holding a billion keys finds one in about 30 steps. Add another billion and it takes 31.

Deriving it

Count how many times the innermost line runs as a function of n. Drop constants and lower-order terms.

for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++)
        sum += a[i][j];
// n · n  →  O(n²)
for (int i = 1; i < n; i = i * 2)
    sum += i;
// i: 1,2,4,8,…  how many
// until n?  →  O(log n)

Amortized: the subtlety in week one

A resizing array doubles its capacity when it fills. That one insert is O(n) because everything gets copied. But it only happens after n cheap inserts, so the average across many operations is O(1). That’s amortized constant time, and it’s why ArrayList.add is called O(1) even though it’s occasionally expensive.

Start here if Big-O never clicked

In plain English

Big-O is not about time. It's about how much worse things get when the pile gets bigger. That's the only question it answers.

You're not computing a number. You're answering: if I double the input, does the work stay the same, go up a little, double, or explode?

Think of it like

You're looking for one specific page in a book.

O(n) is starting at page 1 and flipping forward until you find it. Twice as many pages, twice as much flipping.

O(log n) is opening to the middle, seeing you've gone too far, and opening to the middle of what's left. Every look throws away half the book.

O(1) is knowing it's page 412 and going straight there. The book's size is irrelevant.

A 200-page book and a 2,000-page book take the same effort in the third case, and ten times the effort in the first. That gap is Big-O.

Why the logarithm shows up everywhere in this course

Students get told "binary search is log n" and memorize it without ever seeing why. Here's the whole thing in one line:

Think of it like

A tournament bracket. 64 teams, and each round eliminates half. How many rounds until one winner? 64 → 32 → 16 → 8 → 4 → 2 → 1. Six rounds.

log₂(64) = 6. The logarithm is just "how many halvings to get to one."

Anything that repeatedly discards half its remaining work is O(log n). Binary search does it. Searching a balanced tree does it. That's the entire family.

And the reason it matters so much: log grows absurdly slowly. A thousand items takes ~10 steps. A million takes ~20. A billion takes ~30. To make a log-n algorithm take twice as long, you have to square the input.

Reading a loop, mechanically

Three rules cover almost everything you'll be asked.

  1. A loop that touches each item once is O(n). Looking at i++ tells you it's stepping one at a time, so it runs n times.
  2. A loop inside a loop, both over n, is O(n²). The inner one runs fully for every single step of the outer one: n × n.
  3. A loop where the counter multiplies or divides is O(log n). i = i * 2 or hi = mid - 1 means you're skipping, not stepping.

Then drop the small stuff. If you count 3n² + 500n + 9000 operations, that's O(n²). At n = 1,000,000 the n² term is a million times bigger than everything else combined — the rest is noise.

Where people go wrong

Wrong: "O(n²) is always slower than O(n), so I should never write a nested loop."

Right: Big-O describes behavior as n grows large. For n = 10, an O(n²) algorithm with a tiny constant can easily beat an O(n log n) one with heavy setup. Big-O tells you which one wins eventually, not which one wins today.

Where people go wrong

Wrong: "Two nested loops means O(n²)."

Right: Count what the loops actually do. for (i=0; i<n; i++) for (j=0; j<10; j++) is O(n) — the inner loop is a fixed 10, not n. And for (i=0; i<n; i++) for (j=i; j<n; j++) runs about n²/2 times, which is still O(n²) once you drop the constant. Read the bounds, don't count the braces.

Amortized, and why it isn't cheating

Think of it like

Rent. You pay it once a month, not daily — but if someone asks "what does living here cost per day?", dividing by 30 is the honest answer. You don't say "living here is free 29 days and catastrophic on the 30th."

A resizing array works the same way. Most add calls are instant. Occasionally the array fills, and it allocates a new one twice the size and copies everything — that single call is O(n). But it only happens after n cheap calls, so the cost averaged over all the calls is constant. That's amortized O(1).

The doubling is the key. If the array grew by one slot each time instead, you'd copy on every single insert and the true cost would be O(n) per operation. Doubling is what spreads the expense thin enough to disappear.

Symbol tables, and the problem they can’t solve yet

A symbol table is a set of key–value pairs with two operations: put(key, value) and get(key). That’s it. Every structure in the rest of the course is an attempt to make both of them fast at the same time.

This is the entire motivation

Sorted arrays search fast but insert slowly. Linked lists insert fast but search slowly. Neither is good at both. When your instructor introduces binary search trees next week, they are answering the question this table just asked.

Why binary search needs a sorted array

Binary search only works if you can jump to the middle in constant time and the data is in order. A linked list gives you order but no jumping — reaching the middle costs n/2 steps, which destroys the whole advantage. That tension is what a tree resolves: it keeps things ordered while still letting you skip half the data in one comparison.

Start here: what a symbol table actually is

In plain English

A symbol table is a thing you put stuff into with a label, and get stuff out of by that label. Two operations: put(key, value) and get(key).

You've used one every time you wrote HashMap. This course is about building it.

Think of it like

The contacts app on your phone. You don't scroll to find "Mom" — you type the name (the key) and get back the number (the value). You never care where it's physically stored.

Every structure in the next nine weeks is a different answer to one question: how do you find "Mom" fast when there are ten million contacts?

Why the naive answers aren't good enough

Try to build a contacts app with what you already know from CSC 300, and you get stuck in a specific way. Watch it happen:

  1. Unsorted array. Adding is instant — throw it on the end. But finding "Mom" means checking every entry until you hit it. Ten million contacts, ten million checks. O(n) search
  2. Sorted array. Now you can binary search — 24 checks for ten million. But inserting a new contact means shifting everything after it over by one to make room. O(log n) search O(n) insert
  3. Linked list. Inserting is instant — rewire two pointers, no shifting. But now you can't binary search, because you can't jump to the middle. You'd have to walk there. O(1) insert O(n) search

Every option is fast at one thing and slow at the other. That's not a coincidence and it's not you missing a trick — it's a genuine structural tension.

Think of it like

A bookshelf you keep alphabetized. Finding a book is easy — you scan to roughly the right letter and you're there.

But shelving a new "C" book means physically sliding every book from C to Z over by one slot. The thing that makes it easy to search is exactly the thing that makes it painful to update.

A binary search tree is what you get when you stop trying to keep everything in a physical line.

The one line worth memorizing from binary search

int mid = lo + (hi - lo) / 2;

Not (lo + hi) / 2. Those are mathematically identical but lo + hi can overflow past Integer.MAX_VALUE on a large array and go negative, producing a negative index. This is a famous bug that sat in Java's own library for nine years. Write it the safe way out of habit and you'll never think about it again.

Where people go wrong

Wrong: "Binary search is faster, so I should always sort first and then binary search."

Right: Sorting costs O(n log n). If you're only searching once, a plain O(n) scan is cheaper than sorting first. Sorting pays for itself when you'll search many times — that's the whole reason a symbol table is a persistent structure and not a one-off function.

Ordered operations — the reason trees beat hash tables sometimes

A sorted structure gives you more than get. It gives you min, max, "all keys between X and Y", "the largest key not exceeding X", and iteration in sorted order. Hash tables can do none of these — they scatter keys on purpose.

That's the tradeoff you'll be asked to reason about on the exam, so it's worth naming now: hashing buys raw speed by destroying order. Trees keep order and pay a log n for it.

Deletion, the part everyone loses points on

Removing a node with zero or one child is easy — promote the child. The hard case is two children, and the trick is Hibbard deletion: replace the node with its successor, the smallest key in its right subtree. That key is the only one that can sit there without breaking the ordering, because everything left of it is smaller and everything right is bigger.

private Node delete(Node x, Key key) {
    if (x == null) return null;
    int cmp = key.compareTo(x.key);
    if      (cmp < 0) x.left  = delete(x.left,  key);
    else if (cmp > 0) x.right = delete(x.right, key);
    else {
        if (x.right == null) return x.left;   // 0 or 1 child
        if (x.left  == null) return x.right;
        Node t = x;                            // 2 children:
        x = min(t.right);                      // grab successor
        x.right = deleteMin(t.right);
        x.left  = t.left;
    }
    x.size = size(x.left) + size(x.right) + 1;
    return x;
}

Traversals

All three recursive traversals are the same three lines — only the position of the visit moves.

private void inorder(Node x) {
    if (x == null) return;
    inorder(x.left);              // everything smaller
    System.out.println(x.key);    // ← move this line
    inorder(x.right);             // everything bigger
}

Put the visit before both calls and it’s preorder; between them, inorder; after both, postorder. Inorder on a BST prints keys in sorted order — that isn’t a coincidence, it’s the defining property restated, and it’s an exam question most quarters.

Level-order is the odd one out: it isn’t recursive at all, it uses a queue. Which is exactly BFS on a graph, five weeks early.

Start here: the BST in plain English

In plain English

A binary search tree is a bunch of boxes. Each box holds a key and points to at most two other boxes: a "smaller" one on the left and a "bigger" one on the right.

That's it. The magic comes entirely from one rule being true at every single box, not just the top one.

Think of it like

Twenty Questions, but the questions are chosen for you.

You're looking for 40. You start at the root, 50. "Is 40 less than 50?" Yes — so go left, and you have just eliminated every number on the right side of the tree without looking at a single one of them.

Each node isn't one comparison. It's one comparison that deletes half the remaining possibilities.

Searching, step by step

Looking for 40 in the tree 50 / 30, 70 / 20, 40, 60, 80:

  1. Start at 50. Is 40 < 50? Yes → go left. 70, 60, and 80 are now eliminated. Three nodes gone, one comparison.
  2. Now at 30. Is 40 < 30? No, it's bigger → go right. 20 is eliminated.
  3. Now at 40. Equal → found it. Three comparisons for seven nodes.

Scale that up. A balanced tree with a million nodes finds any key in about 20 comparisons. A linear scan would average 500,000.

Insertion is just a failed search

In plain English

To insert, you search for the key as if it were already there. When you run off the bottom of the tree and hit a null link, that empty spot is exactly where the key belongs. Put it there.

You never rearrange anything. New nodes always arrive as leaves.

This is why insertion and search cost the same, and why they're the same code with a different ending. If you understand one, you understand the other.

Where people go wrong — the #1 documented BST error

Wrong: Inserting a key by finding "a node with a free slot" and hanging it there.

Right: There is exactly one legal position for a new key, and the search path finds it. If you put 40 anywhere else — even somewhere with a conveniently empty child pointer — you break the invariant, and every future search for 40 will walk past it and report "not found." The structure isn't a container, it's a set of promises about where things are.

Where people go wrong — the #2 documented BST error

Wrong: "Binary search trees are balanced, so operations are O(log n)."

Right: A plain BST has no balancing whatsoever. Its shape is entirely decided by the order the keys arrived in. Insert sorted data and you get a linked list with extra steps: O(n). Press Insert in order in the visualizer above and watch it happen. The honest statement is "O(h), where h is the height" — and h is O(log n) only if you got lucky or used a balanced tree.

Why the left rule must hold everywhere

Think of it like

A company org chart where everyone alphabetically before you is somewhere down your left branch and everyone after you is down your right — and that's true for every employee, not just the CEO.

If one middle manager has someone mis-filed, then everyone searching through that manager gets sent the wrong way. One local violation breaks an entire subtree.

The three deletion cases

Deletion is the only genuinely fiddly BST operation, and it's fiddly for one reason: removing a node leaves a hole that something has to fill legally.

  1. No children (a leaf). Just remove it. Nothing pointed through it, so nothing breaks.
  2. One child. Promote the child into the gap — like removing a link from a chain and joining the two ends. Everything below was already on the correct side.
  3. Two children. You can't promote either child, because each has its own subtree that has to stay put. You need a key that can legally sit in that exact spot.
Think of it like

A manager leaves. You can't promote a random person — you need someone who fits between everyone below them and everyone above them.

The successor is the smallest key in the right subtree: the very next value in sorted order. Everything in the left subtree is still smaller than it, and everything remaining in the right subtree is still bigger. It's the only person who fits without reshuffling the org.

Go right once, then left as far as you can. That's your replacement.

Reading the recursive shape

private Node put(Node x, Key key, Value val) {
    if (x == null) return new Node(key, val);   // found the empty spot
    int cmp = key.compareTo(x.key);
    if      (cmp < 0) x.left  = put(x.left,  key, val);
    else if (cmp > 0) x.right = put(x.right, key, val);
    else             x.val   = val;
    x.size = size(x.left) + size(x.right) + 1;
    return x;
}
In plain English

The line x.left = put(x.left, key, val) confuses almost everyone. Read it as: "whatever my left subtree becomes after the insert, that's my new left subtree."

Most of the time the answer is "the same thing it already was" and the assignment does nothing. But at the very bottom, put(null, ...) returns a brand-new node, and that assignment is what actually attaches it to the tree. Without the assignment, you'd create the node and immediately throw it away.

Think of it like

Passing a form down a chain of desks and each person handing back the (possibly updated) folder they got. Almost everyone hands back the identical folder. Only the last desk puts a new page in — but every desk in the chain has to accept the folder back, or the new page never makes it up to the top.

Balanced trees

A plain BST degrades to a linked list on sorted input. A red–black tree refuses to: it rebalances on the way back up from every insertion, and guarantees O(log n) no matter what order the keys arrive in.

First, 2–3 trees — the idea

Allow nodes to hold two keys and have three children. When a node overflows to three keys, it splits: the middle key moves up to the parent, and the node becomes two nodes.

Because splits push growth upward rather than downward, every leaf stays exactly the same distance from the root. The tree is perfectly balanced by construction. The catch is that implementing 2–3 trees directly means juggling two different node types, which is miserable in code.

The move

A red–black tree is a 2–3 tree in disguise. A red link glues two ordinary BST nodes together to represent one 3-key node. So you get 2–3 balancing while writing plain binary-node code. That’s the whole trick, and understanding it makes the rotation rules stop feeling arbitrary.

Start here: why balancing exists at all

In plain English

A plain BST is only fast if it's bushy. Feed it sorted data and it grows into a single long vine, and you're back to scanning one item at a time.

A balanced tree is a BST that refuses to get tall. It does a little rearranging after every insert to keep itself short, and that rearranging is the entire content of weeks 3 and 4.

Think of it like

Stacking boxes. If you always put the new box on top of the same pile, you end up with one tower twenty boxes high and reaching the bottom one is a chore.

A balanced tree is a warehouse worker who, every time a pile gets too tall, shuffles boxes sideways so no pile is ever much taller than any other. It's a bit of work on every insert, but nothing is ever buried deep.

You pay a small, constant cost on every insert to guarantee you never pay a huge one on a search.

2–3 trees: the honest version of the idea

In plain English

A normal tree node holds one key and has two children. A 2–3 tree lets a node hold two keys and have three children when it needs to.

That flexibility is the trick: when a node gets too full, instead of growing a new level downward, it pushes a key upward into its parent.

Think of it like

An elevator with a strict capacity. Two people fit fine. A third steps in and the alarm goes off, so the middle person gets pushed out to the floor above.

Now here's the part that makes it work: pushing upward means the tree can only ever get taller at the very top, all at once. Every leaf stays exactly the same distance from the root — automatically, with no extra bookkeeping.

Ordinary trees grow downward and get lopsided. A 2–3 tree grows upward and can't.

So why don't we just implement 2–3 trees directly? Because in code you'd need two different node types, different comparison logic for each, and a pile of special cases for splitting. It's correct and it's miserable.

Red–black trees: a 2–3 tree in a costume

In plain English

A red–black tree gets 2–3 balancing while using nothing but ordinary two-child nodes. It does this by coloring links.

A red link means "these two nodes are really one node." A black link is a normal parent–child link.

Think of it like

Two roommates sharing one apartment. From the street it looks like two separate people at two addresses. But mail addressed to the apartment reaches either of them — the building treats them as one unit.

A red link is the "these two share an apartment" marker. When you count how tall the building is, a red link doesn't count as a floor.

That's why "every path from root to leaf has the same number of black links" is the balance condition. Red links are free.

The two moves, in plain English

Think of it like

A rotation is a see-saw. Three nodes in a row, leaning one way. Push down on the high end and the middle one rises to become the new top, with the other two hanging off it. Nothing changes about which keys are bigger or smaller — you've only changed who's holding whom.

A color flip is the elevator alarm going off. Both children red means you've got three keys crammed into one conceptual node. Flipping colors sends the middle key's link upward — that's the 2–3 split, in disguise.

Where people go wrong

Wrong: "Rotations reorder the keys."

Right: A rotation never changes the sorted order of the keys — that's what makes it safe. Do an inorder traversal before and after a rotation and you get the identical sequence. All it changes is the shape: who is whose parent. If your rotation changes the inorder output, you've written it wrong.

Where people go wrong

Wrong: "The three fix-up rules are three separate cases, so I check which one applies."

Right: They run in sequence, all three, every time, at every node on the way back up. Each one sets up the next: a left rotation can create the two-reds-in-a-row that the second rule fixes, which can create the both-children-red that the third rule fixes. Treating them as mutually exclusive cases is why people's implementations break on the third insert.

Why "left-leaning"?

Sedgewick's version requires every red link to lean left. That's not a mathematical necessity — it's a simplification. Allowing red links on either side means twice as many cases to handle. Forcing them all to one side cuts the implementation down to the eleven lines you saw above.

So rule one, "right child red → rotate left," isn't fixing an imbalance. It's normalizing, so the other two rules only ever face one shape.

What you actually have to know for the exam

Not the proof. You need to be able to: (1) insert a sequence of keys by hand and draw the result, (2) say which rule fires and why at each step, (3) explain that the guarantee is height ≤ 2 log n, and (4) say what a red link represents in the equivalent 2–3 tree.

Insert 1, 2, 3 into an empty tree on paper until you can do it without hesitating. Then 1 through 7. That covers every case you'll be shown.

Hash tables

Trees get you O(log n) by comparing. Hash tables aim for O(1) by computing where a key belongs — no comparisons at all. The entire difficulty is what to do when two keys compute the same slot.

Deliberately cause a collision

With M = 7, the keys 3, 10, 17, and 24 all hash to slot 3. Insert them in order under each strategy and watch what differs:

  • Separate chaining hangs a linked list off slot 3. The slot count never changes; the chain just gets longer, and search cost grows with chain length.
  • Linear probing walks forward to the next empty slot. Keys end up in slots that aren’t their hash value, which is why deletion is genuinely tricky — blanking a slot can orphan every key that probed past it.
The honest caveat about O(1)

Hash tables are O(1) on average, assuming keys spread evenly. With adversarial or badly-distributed keys, every key lands in one slot and you’re back to O(n). A red–black tree’s O(log n) is a guarantee; a hash table’s O(1) is an expectation. Knowing which you need is the point of the “choose the right structure” exam question.

What makes a hash function acceptable

  • Deterministic. The same key must always produce the same value, for the life of the table.
  • Uniform. Keys should scatter across all M slots. Clustering is what turns O(1) into O(n).
  • Cheap. If hashing costs more than a few comparisons, you should have used a tree.
  • Consistent with equals. If a.equals(b), then a.hashCode() == b.hashCode() — always. Override one without the other and your objects vanish inside HashMap.

Start here: hashing in plain English

In plain English

Every structure so far searched for a key by comparing it to other keys. A hash table doesn't search at all. It does arithmetic on the key to calculate which slot the key lives in, then goes straight there.

No comparisons, no walking a tree. One calculation, one jump.

Think of it like

A coat check at a theater. You don't hand over your coat and have the attendant search the racks. They give you ticket #47, and your coat goes on hook 47. When you come back, they walk directly to hook 47.

The hash function is the rule that turns your coat into a hook number. The table is the rack of hooks.

It doesn't matter whether there are 50 coats or 50,000 — going to hook 47 takes the same time. That's what O(1) means here.

The problem: two coats, one hook

With 7 hooks and the rule hash(k) = k % 7, the keys 3, 10, 17, and 24 all produce hook 3. That's a collision, and it isn't a rare accident — it's guaranteed. You have infinitely many possible keys and a finite number of hooks.

So the entire design of a hash table is really the answer to one question: what do you do when the hook is already taken? There are two standard answers.

Think of it like — separate chaining

Hang a second coat on the same hook. And a third. Hook 3 becomes a little rack of its own.

Finding your coat is now: jump to hook 3 (instant), then look through the coats hanging there (a short list). If the hash function spreads things evenly, that list stays about one or two items long, so it's still effectively instant.

Fast as long as the chains stay short. A chain of 500 means you built a linked list and wasted your time.

Think of it like — linear probing

A parking lot. Your assigned spot is #3, but someone's in it, so you take #4. If that's taken too, #5.

Retrieving is the same walk: go to #3, is it your car? No — check #4. Keep going until you find it or hit an empty space, which proves it was never parked.

One item per slot, no side lists. But if the lot gets full, you drive a long way from your assigned spot.

Load factor: the one number that decides everything

In plain English

Load factor = how full the table is. 50 keys in a 100-slot table is 0.5.

This single number controls whether a hash table is fast or a disaster. Chaining stays fine up to about 1.0 (average chain length of one). Linear probing needs to stay under about 0.5 — above that, occupied runs merge into long clumps and probes get long.

When the table crosses its threshold, a real implementation resizes: allocates a bigger array and rehashes every key into it. Same doubling trick as a resizing array, same amortized-O(1) result.

Where people go wrong

Wrong: "You rehash by copying the keys into the same slots in the bigger array."

Right: Every key must be re-hashed, because the slot depends on the table size. If M goes from 7 to 14, then k % M changes for nearly every key. Copying slot-for-slot leaves keys in positions where lookup will never find them.

Why deleting from a probing table is a trap

Think of it like

Cars parked at #3, #4, #5 — all originally assigned #3. The #4 car leaves and you just empty the space.

Now someone looks for the #5 car. They check #3 (not it), check #4 (empty!) and conclude the car was never parked — because an empty slot is the signal for "stop looking." You've made a car that's physically right there unreachable.

This is why probing deletion either re-inserts everything downstream of the hole, or leaves a "tombstone" marker meaning "empty, but keep walking."

What makes a hash function good

  1. Deterministic. The same key must always give the same slot. Anything involving randomness or the current time makes your data unfindable.
  2. Uniform. Keys should scatter evenly. A function returning 3 for everything is a valid function and a useless hash — you've built one long linked list.
  3. Cheap. If hashing costs more than a handful of comparisons, a tree would have been faster.
  4. Consistent with equals. If a.equals(b) then a.hashCode() must equal b.hashCode(). Break this and objects vanish inside HashMap.
Think of it like — the equals/hashCode contract

Two identical twins walk into the coat check. The rule says identical people get the same hook number. If the attendant gives twin A hook 12 and twin B hook 30, then twin B comes back, gets sent to hook 30, and their (identical) coat is on hook 12. It's right there in the building and permanently unreachable.

Vertices and edges. Every graph algorithm in this course is a variation on visiting vertices without visiting any of them twice — and the two fundamental ways to do that differ by exactly one data structure.

The only difference

Run both above on the same graph and compare the visit orders. DFS dives as deep as it can before backing up; BFS fans out in rings by distance from the start. Now look at the code:

// DFS — recursion IS the stack
private void dfs(Graph G, int v) {
    marked[v] = true;
    for (int w : G.adj(v))
        if (!marked[w]) {
            edgeTo[w] = v;
            dfs(G, w);
        }
}
// BFS — an explicit queue
private void bfs(Graph G, int s) {
    Queue<Integer> q = new LinkedList<>();
    marked[s] = true; q.offer(s);
    while (!q.isEmpty()) {
        int v = q.poll();
        for (int w : G.adj(v))
            if (!marked[w]) {
                marked[w] = true;
                edgeTo[w] = v;
                q.offer(w);
            }
    }
}
Write these side by side

Structurally they are the same algorithm: mark, look at neighbors, recurse or enqueue. Stack → depth. Queue → breadth. Because BFS pulls vertices in the order they were discovered, it reaches every vertex by the fewest possible edges — which is why BFS gives shortest paths on an unweighted graph and DFS does not.

Representing a graph

The standard choice is an adjacency list: an array indexed by vertex, each entry holding a list of that vertex’s neighbors. For the sparse graphs that occur in practice it beats an adjacency matrix on both space and iteration speed.

public class Graph {
    private final int V;
    private Bag<Integer>[] adj;    // one bag per vertex

    public void addEdge(int v, int w) {
        adj[v].add(w);
        adj[w].add(v);              // undirected: both ways
    }
}

Delete that second line and you have a digraph — week 8. That one-line difference is the whole distinction, and it's what makes cycle detection and topological sort possible.

Start here: graphs in plain English

In plain English

A graph is dots connected by lines. The dots are vertices, the lines are edges. That's the whole definition.

Trees were graphs all along — just very tidy ones with no cycles and a designated top. Graphs drop both of those restrictions, which is what makes them able to model almost anything.

Think of it like

A subway map. Stations are vertices, track between them are edges.

"Can I get from here to there?" is connectivity. "What's the fewest stops?" is shortest path. "Which tracks could we keep and still reach every station?" is a spanning tree. Every graph algorithm in this course is one of those three questions.

How you actually store one

Think of it like

An adjacency list is a contacts list: for each person, the names of their friends. Compact, and it's instant to list one person's friends.

An adjacency matrix is a giant spreadsheet with every person as both a row and a column, with a checkmark in each cell where two people are friends. Instant to answer "are these two specific people friends?" — but for a school of 10,000 people it's 100 million cells, nearly all empty.

Real graphs are sparse — most people know a few dozen people, not thousands. So adjacency lists win, and that's what Sedgewick uses.

DFS and BFS, the only two ways to explore

Think of it like — DFS

Exploring a hedge maze by always taking the first turn you see and committing. You go deep, hit a dead end, back up to the last junction you hadn't finished, and try the next branch there.

You'll cover the whole maze. But the path you took to any given spot may be absurdly long, because you never stopped to consider shortcuts.

Think of it like — BFS

Dropping a stone in a pond. The ripple reaches everything one step away, then everything two steps away, then three.

Because you finish an entire ring before starting the next, the first time you reach any vertex, you reached it in the fewest possible steps. That's not a bonus feature — it's a direct consequence of the ordering.

DFS answers "can I get there?". BFS answers "what's the shortest way?".

The only real difference in the code

Both algorithms are: mark a vertex, look at its neighbors, put the unvisited ones somewhere, repeat.

The "somewhere" is the whole difference. A stack hands back the most recent thing you added, so you keep diving into the newest branch — depth. A queue hands back the oldest, so you finish the current ring first — breadth.

DFS usually uses recursion, which is a stack — the call stack. That's why DFS looks shorter: Java is managing the stack for you.

Where people go wrong

Wrong: Forgetting the marked[] array, or marking too late.

Right: Without marking, a cycle makes you loop forever — A sends you to B, B sends you back to A, forever. And in BFS you must mark a vertex when you enqueue it, not when you dequeue it, or the same vertex gets added to the queue several times before it's ever processed.

Where people go wrong

Wrong: "DFS finds the shortest path if I just track distances."

Right: DFS reaches vertices by whatever branch it happened to dive down first, which can be wildly longer than necessary. Tracking the distance faithfully records a bad answer. Only BFS's ring-by-ring order guarantees minimum edge count.

Directed graphs — one line different

Everything above assumed edges go both ways. Delete the second line of addEdge and they don't:

Think of it like

Friendship versus following. Friendship is mutual — an undirected edge. Following is not: you can follow someone who doesn't follow you back. That's a directed edge.

Course prerequisites are directed too, and that's where topological sort comes in: given "CSC 300 before CSC 301," produce a valid order to take everything. If there's a cycle — A requires B requires A — no valid order exists, which is exactly what cycle detection tells you.

Minimum spanning trees

Think of it like

You're wiring internet to every house in a neighborhood. Each possible cable run between two houses has a cost. You need every house connected, and you want to spend the least money.

You don't need a cable between every pair — just enough that everyone's reachable. With n houses, that's exactly n−1 cables, and no loops (a loop means one cable you could cut and still have everyone connected).

That's a minimum spanning tree: connect everything, no cycles, cheapest total.

The shape

Nodes hold no key at all. The key is the path you took to reach the node. A node carries a value only if some key ends exactly there, which is why sea and seashore coexist without conflict — one just stops earlier along the same path.

private static class Node {
    private Object val;                // null unless a key ends here
    private Node[] next = new Node[R];  // R = alphabet size
}

private Node get(Node x, String key, int d) {
    if (x == null) return null;
    if (d == key.length()) return x;   // consumed the key
    char c = key.charAt(d);            // dth character
    return get(x.next[c], key, d + 1);

Same recursive shape as the BST’s get, with one change: instead of comparing keys to choose a branch, you use the d-th character as the array index. No comparison happens at all.

Start here: tries in plain English

In plain English

Every structure so far treated a key as one blob to compare. A trie breaks the key into characters and spends one node per character.

The nodes don't store keys at all. The key is the path you walked to get there.

Think of it like

A library where you find a book by spelling it. First hallway: pick the door marked S. Next hallway: pick H. Then E. You're standing in the "she" room.

The rooms have no labels — the label is the sequence of doors you went through. And "shore" shares your first two doors, then diverges. That shared prefix is stored exactly once.

Looking up a 5-letter word takes 5 steps whether the library holds 100 words or 100 million.

Why "it doesn't depend on n" is the whole point

A balanced tree storing a million words needs ~20 comparisons, and each comparison compares whole strings. A trie needs one array lookup per character — 5 steps for a 5-letter word, regardless of how many words are stored.

And a search miss is often even faster. Look up "zqx" and you fail at the very first door, because no key starts with z. You never touched the other 999,999 words.

The operation nothing else can do

Think of it like

Autocomplete. You type "str" and want every word beginning with it.

In a trie: walk three doors to the "str" room, then collect everything in the rooms beyond it. You never look anywhere else in the building.

In a hash table this is impossible — hashing deliberately scatters "street" and "strong" to unrelated slots. In a balanced tree you'd have to scan a range and compare prefixes on every key.

keysWithPrefix is why tries exist, and it's why your phone keyboard uses one.

Where people go wrong

Wrong: "Every node in a trie holds a key."

Right: Most nodes hold nothing. A node has a value only if some key ends exactly there. That's how "sea" and "seashore" coexist on the same path — you walk through the "sea" node (which has a value) and keep going. If you assume every node is a key, you'll report "seas" as stored when it isn't.

The cost: space

An R-way trie gives every node an array of R child references — 26 for lowercase letters, 256 for extended ASCII. Nearly all of them are null. A trie of a few hundred words can allocate hundreds of thousands of empty references.

That's the tradeoff, and it's what ternary search tries (also §5.2) fix: instead of R children, each node has three — less, equal, greater — so you only pay for characters that actually occur.

Drills

Answer each one out loud or on paper before expanding it. A drill you read the answer to teaches you nothing — the retrieval is the whole mechanism.

Foundations

What two things must every recursive method have?

A base case answered without recursing, and a recursive case that calls itself on a strictly smaller input. Missing the first, or failing at the second, gives you StackOverflowError.

Why is binary search O(log n)? Use the word “half.”

Each comparison discards half of what remains. From n items you can only halve about log₂n times before one is left. Doubling n adds a single step.

Two variables point at the same array. You change element 0 through one. What does the other see?

The change. Both hold references to one array — there is only one object. This is why passing a node into a method lets that method mutate your tree.

A sorted array and a linked list are each bad at something. What, and what fixes both?

Sorted arrays search in O(log n) but insert in O(n). Linked lists insert in O(1) but search in O(n). A binary search tree gets O(log n) for both — as long as it stays balanced.

Trees

Which traversal prints a BST’s keys in sorted order, and why that one?

Inorder. It visits the entire left subtree (everything smaller), then the node, then the right subtree (everything bigger) — which is the BST invariant restated as an order of operations.

Deleting a node with two children: which key replaces it, and why is it the only choice?

The successor — the minimum of the right subtree. It’s the smallest key still larger than everything on the left, so it’s the one key that keeps both subtrees valid where they are. (The predecessor, max of the left subtree, works symmetrically.)

Insert 1, 2, 3, 4, 5 into an empty BST in that order. Draw it. What’s the height?

A straight right-leaning line: height 4, search cost O(n). The tree bought you nothing. This degenerate case is the entire reason balanced trees exist.

State the three red–black fix-up rules in order.

1. Right child red and left child black → rotate left.
2. Left child red and its left child red → rotate right.
3. Both children red → flip colors.

Applied bottom-up after the recursive insert. Order matters — each rule sets up the next.

What does a red link actually represent?

Two BST nodes glued into one 3-key node of the equivalent 2–3 tree. Red–black trees are 2–3 trees encoded with ordinary binary nodes, which is why the balancing works out to the same guarantee.

Hashing

Keys 3, 10, 17 with M = 7. Where does each go under chaining? Under linear probing?

All three hash to slot 3. Chaining: all three live in slot 3’s linked list. Linear probing: 3 → slot 3, 10 → slot 4, 17 → slot 5.

Why is a hash table’s O(1) weaker than a red–black tree’s O(log n)?

O(1) is an average that assumes keys spread evenly. Adversarial or clustered keys pile into one slot and degrade to O(n). The tree’s O(log n) is a worst-case guarantee, with no assumption about the keys.

You override equals but not hashCode. What breaks?

Two equal objects can hash to different slots, so a key you just inserted becomes unfindable. The contract is one-directional: equal objects must have equal hash codes.

Graphs

What is the single code difference between DFS and BFS?

The container holding vertices waiting to be processed. DFS uses a stack (usually the implicit call stack); BFS uses a queue. Everything else is identical.

Which one gives shortest paths on an unweighted graph, and why?

BFS. A queue processes vertices in discovery order, so every vertex at distance k is reached before any at distance k+1. DFS commits to one branch and can reach a vertex by a long path first.

How do you turn undirected-graph code into a digraph?

Delete the second line of addEdge — add w to v’s list but not v to w’s. That single change is what makes cycle detection and topological sort meaningful.

Why is DFS worth learning properly in week 8?

Connected components, cycle detection, and topological sort are all DFS with a small addition. Weeks 9 and 10 are largely paid for by week 8.

Choosing a structure

You need keys in sorted order and range queries. What do you use?

A balanced BST (red–black tree / TreeMap). Hash tables have no order at all, so a range query degrades to scanning everything.

You need the fastest possible exact lookup and never need order. What do you use?

A hash table (HashMap). O(1) average beats O(log n), as long as your hash function distributes well and worst-case guarantees don’t matter.

You need every key starting with “str”. What do you use?

A trie. Walk to the prefix node, collect the subtree beneath it — costs O(L + number of matches) and never touches unrelated keys. Trees and hash tables both need a full scan.

Heaps

The course catalog lists heaps alongside trees and hash tables, and Prim's and Kruskal's algorithms both need one. A heap answers a different question from a BST: not "where is key X?" but "what's the biggest thing in here?"

Also skipped, also needed for MSTs

Like union-find, heaps often get no week of their own — but Prim’s algorithm repeatedly asks for the cheapest edge crossing a cut, which is a priority queue, which is a heap. It stays standard exam material either way. Read it before you reach minimum spanning trees.

In plain English

A heap is a tree with one rule: every parent is bigger than both of its children. (That's a max-heap. Flip it for a min-heap.)

Notice what that rule does not say. It says nothing about left versus right. Siblings are in no particular order. The only thing you know for certain is that the largest item in the whole structure is sitting at the root.

Think of it like

A corporate hierarchy where every boss earns more than their direct reports.

Ask "who's the highest paid?" and you don't search — it's the CEO, by definition. But ask "does anyone earn exactly $85,000?" and you're stuck searching the whole company, because two people at the same level have no defined order relative to each other.

A heap is fantastic at one question and useless at every other. That's the trade.

Where people go wrong — documented in the research as a top confusion

Wrong: "A heap is a kind of binary search tree."

Right: They are unrelated shapes with different rules. A BST orders left vs. right (smaller left, bigger right) and is great at finding a specific key. A heap orders parent vs. child and is great at finding the maximum. An inorder traversal of a BST gives sorted output; an inorder traversal of a heap gives nonsense.

The array trick

In plain English

A heap is drawn as a tree but stored as a plain array — no node objects, no left/right pointers at all. Because the tree is always completely filled in, level by level, you can compute where any relative is:

// using 1-based indexing, as Sedgewick does
parent of k   =  k / 2
left child    =  2 * k
right child   =  2 * k + 1
Think of it like

Seat numbers in a theater where the rows double in size: row 1 has 1 seat, row 2 has 2, row 3 has 4. Given your seat number you can compute exactly which seat is "directly behind" you without a map, because the layout never has gaps.

This only works because a heap is always a complete tree — filled left to right with no holes. A BST has arbitrary shape, so it can't do this and needs real pointers.

The two operations, and they're mirror images

Insert — "swim up"

  1. Put the new key at the end of the array (bottom-right of the tree). This keeps the tree complete, but probably violates the heap rule.
  2. Compare it with its parent. If it's bigger, swap them.
  3. Repeat until its parent is bigger, or it reaches the root.
Think of it like

A new hire who's underpaid for their skill. They out-earn their boss, so they swap positions. Then they out-earn that boss, so they swap again — promoted step by step until they land where they belong.

A key can only swim past one level per swap, and the tree is ~log n tall. That's the O(log n).

Remove max — "sink down"

  1. The max is the root, so grab it — that's your answer.
  2. Move the last item in the array into the now-empty root. The tree stays complete, but that item is almost certainly too small to be root.
  3. Compare it with its larger child and swap if the child is bigger.
  4. Repeat until both children are smaller, or it hits the bottom.
Where people go wrong

Wrong: Swapping with either child, or with the left child by default.

Right: You must swap with the larger of the two children. Swap with the smaller one and it becomes the parent of a bigger sibling — you've just created a new violation instead of fixing one.

Why you care: priority queues

Think of it like

A hospital emergency room. It isn't first-come-first-served — the most urgent case goes next, and new arrivals can jump the line.

A plain queue can't do that. A sorted list could, but every arrival costs O(n) to insert in the right place. A heap gives you "add someone" and "take the most urgent" both in O(log n), which is exactly the shape of the problem.

Neither array is good at both. The heap is the compromise that's good enough at both, which is the same story as the BST versus sorted arrays and linked lists — a recurring theme worth noticing.

Where it shows up in week 10: Prim's algorithm repeatedly asks "what's the cheapest edge leaving my blob?" That's a priority queue, and it's why Prim runs in O(E log E).

Union-find

Kruskal's algorithm needs to ask "would this edge create a cycle?" thousands of times, and it needs the answer instantly. Union-find is the structure that gives it. It's also the most elegant thing in the course — the whole implementation is about fifteen lines.

Read this the week before minimum spanning trees

Union-find often appears nowhere in the schedule, but Kruskal’s algorithm is a sorted edge list plus a union-find structure. If you meet both at once in the same lecture, the MST algorithm gets blamed for difficulty that actually belongs to this. Fifteen lines, read a week early, and Kruskal becomes almost trivial.

In plain English

Union-find answers exactly two questions about a set of items:

connected(p, q) — are these two in the same group?
union(p, q) — merge their two groups into one.

It cannot list a group's members, count the groups' sizes cheaply, or undo a merge. Two questions, that's the whole API — and constraining it that hard is what makes it fast.

Think of it like

A party where people cluster into friend groups. Each group picks one person as its spokesperson.

To check whether two people are in the same group, you don't compare guest lists. You ask each of them "who speaks for you?" — and if you keep asking up the chain you eventually reach the spokesperson. Same spokesperson means same group.

To merge two groups, one spokesperson simply starts deferring to the other. Nobody physically moves. One pointer changes and two groups become one.

That's the entire idea. find walks up to the spokesperson; union makes one spokesperson point at another.

Union-find — forest of parent pointers
10 items, each in its own group. Try union 0 1, then 1 2, then 2 3 — and watch the tree depth under each strategy.
root (spokesperson) on the path

Press "Build worst case" under each strategy

That runs union(0,1), union(1,2), union(2,3)… in order — the pattern that ruins naive quick-union.

Under quick-union you get a single vine ten levels deep. Every find now walks the whole thing: O(n). It's the same failure as a BST fed sorted data, and it has the same fix — refuse to let the tree get tall.

Under weighted + path compression the same operations produce a bush two levels deep. Same inputs, completely different structure.

The two improvements

1. Weighting — always hang the smaller tree

Think of it like

Merging two companies. If the 5-person startup's CEO starts reporting to the 500-person company's CEO, only 5 people got a longer chain of command. Do it the other way round and 500 people did.

Always attach the smaller tree under the larger root. A node's depth only increases when its tree is the smaller one, and that can happen at most log n times — because each time it happens, the tree it lives in has at least doubled.

2. Path compression — flatten as you go

Think of it like

Asking your manager who the CEO is, and them asking their manager, and so on up six levels. Once you finally get the answer, everyone in that chain writes the CEO's name on a sticky note.

Next time anyone in that chain is asked, it's one hop instead of six. You did the walk anyway — you may as well record what you learned.

private int find(int p) {
    while (p != parent[p]) {
        parent[p] = parent[parent[p]];   // point at grandparent — halves the path
        p = parent[p];
    }
    return p;
}

public void union(int p, int q) {
    int rp = find(p), rq = find(q);
    if (rp == rq) return;                 // already connected — this is the cycle test
    if (size[rp] < size[rq]) {           // hang the smaller under the larger
        parent[rp] = rq;  size[rq] += size[rp];
    } else {
        parent[rq] = rp;  size[rp] += size[rq];
    }
    count--;
}

Together these give near-constant amortized time — formally O(α(n)), where α is the inverse Ackermann function. For any n you will ever encounter, that value is less than 5. It is not literally O(1), and Sedgewick is careful about that, but the distinction never matters in practice.

Where people go wrong

Wrong: "parent[p] == parent[q] means p and q are connected."

Right: You must compare roots, not parents. Two nodes can sit in the same tree with different immediate parents. find(p) == find(q) is the test; walking all the way up is the entire point of find.

Where people go wrong

Wrong: Thinking the union-find forest is related to the graph you're building.

Right: The forest's shape means nothing about the graph. It's pure bookkeeping about which items share a group. Two vertices joined by an edge in your MST may be far apart in the union-find tree, and that's fine.

Why Kruskal needs exactly this

Kruskal sorts every edge cheapest-first and walks the list, taking an edge unless it would create a cycle. "Would it create a cycle?" means "are these two vertices already connected?" — which is find(v) == find(w).

for (Edge e : sortedEdges) {
    int v = e.either(), w = e.other(v);
    if (uf.find(v) != uf.find(w)) {   // not yet connected → no cycle
        uf.union(v, w);
        mst.add(e);
    }
}
Think of it like

Laying cable between houses, cheapest run first. Before laying each one you ask: "can these two houses already reach each other through cable we've laid?" If yes, this run is redundant — skip it. If no, lay it and the two neighborhoods become one.

Union-find is the clipboard tracking which houses are already on the same network. Without it you'd re-run a graph search before every single edge.

Where the grade actually is

Exam technique

Exams are typically 60% of the grade in this course, and one of the stated learning objectives is to simulate operations on a given data structure — on paper, with no IDE. That's a separate skill from writing the code, and it's the one people neglect.

In plain English

You will be handed a tree and a list of keys and asked to draw what happens. No autocomplete, no compiler telling you that you're wrong, no classmate.

The good news: the question types are extremely predictable. There are about eight of them, and they repeat every quarter. Work through the eight below until they're boring and the exam holds no surprises.

How to hand-trace without making careless errors

  1. Redraw the whole structure after every operation. Do not erase and patch. Erasing is where mistakes hide — you'll fix one link and leave a stale one. Paper is free.
  2. Write the comparison, not just the direction. "40 < 50 → left" rather than an arrow. When you get a wrong answer, you can find the exact step that broke, and partial credit follows the reasoning you showed.
  3. For BSTs, sanity-check with an inorder read. Read your final tree left-to-right. If it isn't in sorted order, you made a mistake — catch it yourself before the grader does.
  4. For red–black trees, apply all three rules at every node. Say them out loud in order as you come back up. Most lost points come from stopping after the first rule that fires.
  5. For heaps, keep the array beside the tree. Update both. If the array has a gap, you broke completeness and something is wrong.
  6. Budget by marks, then move on. A 10-point tracing question is not worth 25 minutes. Leave it, finish the cheap questions, come back.
The most expensive exam habit

Wrong: Doing the whole trace in your head and writing only the final picture.

Right: Write intermediate states. If the final picture is wrong and there's no work shown, that's zero. If your steps are visible and step four has one slip, that's most of the marks.

7 · "You're building a spell-checker that must also suggest completions. Which structure, and why?"

A trie. The justification is what earns marks, so name the operations:

  • Exact lookup ("is this a word?") is O(L) in the key's length, independent of dictionary size.
  • A miss usually fails after one or two characters, which is the common case for a spell-checker.
  • keysWithPrefix gives completions in O(L + number of matches). A hash table can't do this at all — it scatters prefixes deliberately — and a balanced tree needs a range scan with prefix comparisons on every key.

Also state the cost you're accepting: an R-way trie burns space on mostly-null child arrays, and a ternary search trie is the fix if memory is tight. Naming the tradeoff is usually worth a mark on its own.

8 · Give the running time, and justify it.
for (int i = 0; i < n; i++)

Red–black fix-ups

Applied in order, all three, at every node on the way back up:
